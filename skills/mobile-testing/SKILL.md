# Mobile Application Testing

The app as an attack surface and as a specification of the API it talks to. Done = the artifact's identity and build pinned, the posture items each given a disposition with the file or field that showed them, the backend contract reconstructed, and every runtime claim made on a device or emulator you were given, with your own accounts.

## Boundaries

- The app you were authorised to test, on a device, emulator or lab host you control, with accounts you own or were issued. Real user data pulled from a production backend is out of bounds; prove storage and authorisation flaws on your own account and say so.
- The artifact's identity is part of the evidence: package/bundle id, version name and code, and the sha256 of the file you examined. Testing a different build than the one the store serves makes the finding about the wrong thing.
- Runtime instrumentation only on your own device or emulator. Root/jailbreak and hooking frameworks exist to observe the app's own checks, not to attack another tenant's device or instance.
- Discovery of another organisation's app or store listing is public-source work: osint-recon owns the sourcing and its policy gates.
- Deep-link and intent tests target your own install and your own data. Do not drive another app's exported component on the same device unless that app is in scope.
- Not: the backend's authorisation, JWT and business-logic abuse (api-security), login/reset/MFA/SSO state machines (auth-testing), the server-side upload path (file-upload-abuse), the disassembly of native libraries and the deep binary work (rea), the desktop/document execution chain (client-side).
- Stop condition: if the app needs credentials, an MFA code, or a device the engagement did not provide, that is one `ask_operator` request naming the single missing item — not an improvised workaround.

## Procedure

1. Establish what you hold before analysing it: file type, sha256, package identity, version, target SDK / iOS deployment target, and whether the build is a store artifact, a QA artifact, or a debug build (a debug build tells you the engagement is looking at the wrong binary). Deep structure goes to rea; the checks below are the ones that decide the security posture.
2. Manifest and entitlement posture. Android: `debuggable`, `allowBackup` plus `fullBackupContent`/`dataExtractionRules`, `usesCleartextTraffic` and the `networkSecurityConfig` (per-domain exceptions, pinned certificates, trust-anchored user CAs), exported activities/services/receivers/providers and their `intent-filter`s, providers' `grantUriPermissions` and path scopes, `grantUri` URI-permission flags on `FileProvider` paths, `sharedUserId`, permission declarations versus actual use, and `android:scheme`/`host`/`path` deep links (plus App Links `assetlinks.json`). iOS: entitlements (`get-task-allow`, `com.apple.security.application-groups`, keychain access groups, `aps-environment`), `NSAppTransportSecurity` exceptions and `NSAllowsArbitraryLoads`, declared `CFBundleURLTypes` schemes and associated domains (`apple-app-site-association`), `UIFileSharingEnabled`, `LSSupportsOpeningDocumentsInPlace`, `NSLocation*`, background modes, extensions and App Clips. Every one of these is an asset attribute with the field name and value as the evidence.
3. Extracted content review: hardcoded endpoints, hosts, buckets, tenant IDs, third-party service identifiers, Sentry/Datadog-style DSNs, feature flags, debug switches, test accounts, and the client's own version/branch markers. Secrets go to `save_task_credential` and are cited by ID; never written into a fact, finding, or report line. Note which are client-side public keys (a push or analytics key is expected) versus which are server-authoring material.
4. Storage at rest on your own install, with your own account: the app's files (Android `/data/data/<pkg>`, shared storage and external dirs, cache, `WebView` caches, databases, exported `FileProvider` paths; iOS app container, `Documents`, `Library/Caches`, keychain items with their accessibility class, and pasteboard), what tokens and PII are in them, and whether they survive logout, uninstall (Android `allowBackup` plus cloud backup, iOS backup/iCloud), and lock state. Reference a file by path and describe its class and count; do not copy real personal data into the work dir.
5. Transport and pinning: does the app accept a self-signed CA on your own device (a network-security-config that trusts user CAs, or a missing ATS exception being *not* needed), does pinning exist and where does it fail open (pinned host list gaps, a debug-only bypass, an embedded root), and does it fall back to cleartext for any host. Then reconstruct the backend contract: hosts and paths, auth header or cookie shape, tenant/user identifiers the client sends, device-fingerprint and attestation fields, per-request signature fields and where they are computed, version-gating headers, and which endpoints the client calls that the UI never shows. Feed the contract to `insert_assets` (it is inventory); flag the ones that look unauthenticated.
6. Client-side trust the server still honours: every decision the app makes that the backend re-checks or does not — price/quantity/eligibility computed in the client, hidden features gated by a flag or a build type, admin screens reachable from your own session through the API rather than the UI, role claims sent by the client, and the "mobile is exempt" pattern: the same operation with weaker validation, no rate limit, or missing 2FA gating on the mobile variant. The finding is what the backend accepted, not what the UI concealed: reproduce each claim as a direct request against the contract from step 5, using only your own accounts.
7. Runtime observation on your own device/emulator with your own session, when the environment exists: root/jailbreak and emulator-detection behaviour and whether a detected state hard-blocks or merely warns; SSL-pinning failure mode visible in the app's own log; whether the app logs tokens or PII to the system log; screenshot-flagging and background-task content (secure-text field and `FLAG_SECURE` behaviour, iOS `UIApplication` snapshots); WebView configuration (`addJavascriptInterface` and `setJavaScriptEnabled`, `setAllowFileAccess`, `setAllowUniversalAccessFromFileURLs`, `setWebContentsDebuggingEnabled`, and whether an in-app `WebView` loads a remote URL with a JS bridge that any page can reach); keyboard-candidate and cache leakage. Where you cannot run this, record it as NOT ASSESSED with the missing prerequisite named.
8. Deep-link and exported-component surface: craft intents and URLs against your own install that hit exported components, `content://` URIs from a provider, and scheme handlers; test whether a link bypasses the session check, whether a parameter is honoured from the link without authentication (a `userId`, `token`, or `redirect` taken straight from the URL), and whether the app's own web page or push notification can invoke it. On iOS, test the URL scheme and universal-link path against your own account and check the `apple-app-site-association` file the backend serves (an over-broad path prefix is a real link-hijack finding).
9. Server-push and background surfaces: the notification payload's shape and what the client does with an unauthenticated push (a token in a payload, a URL opened on receipt), the webhook/Firebase sender's authority, and any background refresh that runs without a session.
10. Give every tasked posture item an explicit disposition (confirmed, cleared with the field/value or request that cleared it, or not assessed with the reason), and hand what belongs to another seat as a fact: the backend authorisation tests to api-security, login state machines to auth-testing.
11. At wrap-up, state what you did not run because the environment was missing (no device, no lab account, no store access) instead of leaving the reader to assume coverage.

## Evidence

Positive: artifact identity (package, version code, sha256), the exact field, file path, class, method or request that produced the conclusion, the device/OS and app version for anything runtime, which account owned the data observed, and for backend claims the exact request plus what the server accepted with counts (`3 of 3 requests accepted the client-supplied role claim; 0 of 3 the price field`). Distinguish static (read from the artifact) from dynamic (observed executing) per item.

Negative: "`<item>` NOT ASSESSED on `<artifact identity>`: the reason, stated as the missing prerequisite, e.g. no authorised device or emulator was provisioned for this run, so runtime root-detection and `FLAG_SECURE` behaviour could not be exercised". For items you did run and found nothing: "`<item>` tested via `<method>` across `<surfaces>` on `<build>`: `<n>` observations, all `<result>` — `<conclusion>`".

## Report shape

"`<platform> <app id + build>`: `<posture item>` allows `<attacker outcome>` on `<host/endpoint or component>`" with fields: artifact identity and sha256, evidence location (manifest field / file path / class / request), device-OS-app version where runtime was involved, the affected account class and count, static-versus-dynamic basis, and the NOT ASSESSED list for the run.
