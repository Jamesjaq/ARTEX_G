# Threat Emulation (procedure parity from published reporting)

Emulation is a coverage instrument: we reproduce how an actor operates so the client's sensors and people get tested against something with a public history, not against our improvisation. Done means a sourced technique list, an objective tied to the client's own crown jewels, a step-by-step plan expressed as technique → data source → expected detection, a documented subset the RoE actually allows, and every step labelled for provenance so nobody confuses our invention with the actor's procedure.

## Boundaries

- Authorised use only: an emulation plan is executed inside this engagement's scope, against the assets registered for it, in the agreed window. Nothing here may be run against a host or a tenant the RoE has not named.
- Emulate procedure, never the actor's identity. Do not reuse a real group's infrastructure, domains, certificates, hashes, tool binaries, malware names or published IOCs to look convincing. Borrowing a real actor's indicators is a false-flag exercise the client did not commission, and it can pull an unrelated third party or a live investigation into our test.
- The client's crown jewels decide the objective, and the RoE decides the technique set — not the actor's reputation, and not what the bench is capable of.
- Anything plausibly mistakable for a real intrusion against a real person, and anything touching safety, clinical, industrial or regulated systems, goes to the operator before it is tasked; so does anything whose realistic reproduction is destructive (encryption, wipers, deletion, firmware).
- This skill is NOT scope and RoE drafting (that is `engagement-scoping`), NOT the coverage measurement itself (that is `detection-coverage` and `telemetry-sources`), NOT the artifact work (that is `payload-lab-development`), NOT the channel (that is `c2-ops`), NOT graph reachability to the objective (that is `attack-path-mapping`), NOT a vector whose last step is a human (that is `human-terrain`).
- Honesty stop condition: if the reporting is too thin to support procedure parity, say the scenario is under-evidenced. A plausible-looking scenario built on nothing is worse than a shorter one.

## Procedure

1. Fix the actor and the sources, and date them. Pull from at least two independent published reports — vendor APT profiles, government/CISA advisories, ISAC notices, ATT&CK Group pages — and record for each: publisher, publication date, the collection period it describes, and what it claims to be based on. Note where reports disagree; single-source actor profiles decay in months and are often one telemetry slice of one victim.
2. Extract procedure, discard infrastructure. Build a step list of behaviours in the actor's own sequence (initial access style → execution → persistence → credential access → collection → egress) and drop every indicator, hostname, hash, URL and file path. Where a report names a specific tool, keep the behaviour and replace the tool with something engagement-owned or benign.
3. Map each behaviour to ATT&CK, verified rather than remembered. For every step, look up the technique and sub-technique ID against the ATT&CK enterprise matrix (`web_search` plus `WebFetch` of the technique page, which lists applicable data sources and detected-with examples) and write down the ID, the technique name, and the platform/version the page scopes it to. A behaviour with no honest ID gets dropped or recorded as unmapped, not shoehorned into the nearest-sounding T-number.
4. Set the objective on the client's estate, not the actor's history. Take the crown jewels and named in-scope assets from the RoE and `list_assets`, then choose the one path that would actually matter to this client. Write acceptance as an observable outcome, so the run can be scored.
5. Pre-filter the technique list against the RoE — this is the gate between planning and tasking. For each technique record: allowed / allowed-with-conditions (approval naming the asset, window, reversible value) / declined. Decline, and write the reason: destructive or irreversible actions; anything targeting availability of a production service; boot/firmware-level persistence; offline cracking of captured material; actions against real people's accounts or devices without named approval; techniques whose only faithful reproduction would put a real intrusion at a real organisation's door. Keep the declined list in the plan — it is the part of the coverage question the client still needs answered, and it becomes a tabletop or lab item rather than a live step.
6. Express each permitted step as technique → data source → expected detection → verdict owner. Take the data sources from the ATT&CK page for that technique, match them against the sensors the client actually has (from `telemetry-sources` or the engagement's notes), and state what should appear and roughly when. Where the sensor is absent, the expectation is "no coverage", which is a finding before we execute, not after.
7. Add the realism that reporting does not give you, and label it. Provenance per step, mandatory: **attested** (the behaviour is described in the cited reporting, name the source and date), **inferred** (plausible for the actor, extrapolated from adjacent reporting or their typical stack — say which), **invented** (our construction to make the path executable in this environment, e.g. our own implant, our own account names, a benign marker file standing in for a real artifact). Anything invented never presents as an actor technique; it is written as a substitute, and the report names the substitutes.
8. Design the measurement harness alongside the scenario. Agree with the client which detections, tickets and analyst decisions count as success, and set a baseline: the same steps run in a lab image with the sensor stack and no live production exposure, before any live step gets tasked. Lab first, and say which one produced each result.
9. Sequence and hand the plan up before execution: the step list with IDs, objective, allowed/declined table, expected detections, provenance labels, declined list, window, abort triggers, and the named approval per risky step. `report_finding` is not where this surfaces — your lead and the operator approve it before a single intent is created, and the plan lands as facts on the graph so every seat inherits the same labels.
10. Run, then score each step against its expectation with a real count: detected / partially observed / missed, from which source, with what latency, and what the analyst did. Where we simplified a technique, record the simplification in the same line, so the coverage number is honest about the reduced fidelity that produced it. Anything not actually executed stays a plan item and is never reported as coverage.

Gate: do not go to step 6 until step 3 has an ID per step and step 5 has a verdict per step; do not go to step 10 until step 9's plan is approved; do not run any live step whose risky action is not named in an approval.

## Evidence

- Positive (a coverage result): technique and sub-technique ID, platform/version, the step's provenance label, the data source named, the sensor that produced (or failed to produce) the event, latency, the analyst action, and the count against attempts ("3 of 4 steps surfaced via Sysmon plus EDR console; 1 produced no event in either source"). Label proof basis: executed-live, executed-lab, or planned-not-run.
- Positive (a plan): source citations with publication and collection dates, the mapping table, the allowed/declined decision with reasons, and the declined list.
- Negative, honest: "no coverage signal for <technique id> across <N> runs in <window> from <named sources> — reported as a gap, contingent on those sources being instrumented in this estate." And the equally valid one: "cannot verify the sensor path from this position; NOT ASSESSED, needs the client's SIEM export." Where a step was declined on RoE grounds, state the decline rather than implying the control was tested and passed.
- Reporting-currency honesty: name the date you verified the actor profile and the matrix version, and mark anything you did not re-check as unverified.

## Report shape

Title pattern: `Emulation of <actor> procedure: <technique id> <detected / missed> via <sensor source> at <stage>`.
Fields: actor and source citations with dates, matrix version, objective and acceptance bar, technique ID plus name plus platform, provenance label, data source and sensor, expected versus observed, latency and analyst action, count against attempts, proof-basis label, RoE disposition for that step, the declined list with reasons, and the substitutes that stood in for real artifacts.
